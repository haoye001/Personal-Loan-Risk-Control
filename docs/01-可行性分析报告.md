## 1. 引言

### 1.1 编写目的

本文档对“多数据源融合的互联网个人贷款风控系统”基本版进行可行性分析，从技术、经济、操作、法律等维度评估项目实现的可行性，并为后续需求分析、系统设计和代码实现提供决策依据。

### 1.2 项目背景

随着互联网金融的发展，传统银行及贷款金融机构逐渐将个人贷款业务迁移至线上。互联网个人贷款系统需要支持用户在线申请、自动审批、进度查询、还款管理等功能。本课题要求设计开发一个多数据源融合的互联网个人贷款风控系统，本阶段先完成基本版：安卓借款端 App + Web 用户端 + Web 审批管理端 + 后端服务，风控模型仅设计接口。

## 2. 可行性研究前提

### 2.1 系统目标

开发一个互联网个人贷款系统基本版，实现：
- 借款用户可通过 Android App 注册、登录、提交贷款申请、查询进度、查看还款计划。
- 借款用户也可通过 Web 用户端（H5 / Web 页面）完成注册、登录、产品浏览、贷款申请、进度查询、还款计划查看。
- 审批人员可通过 Web 管理端查看申请、进行审批操作、管理用户、查看统计。
- 后端提供稳定的 RESTful API 服务，支撑两端数据交互。
- 预留风控接口，为后续阶段实现多数据源融合风控模型做准备。

### 2.2 主要约束

- 本阶段为课程项目 I，重点在于可行性分析、需求分析、系统设计与代码实现。
- 借款端必须为 Android 平台 App。
- 后端审批管理端为 Web 应用系统。
- 本阶段不实现具体风控模型，仅设计接口。
- 团队仅 3 人，开发周期有限。

## 3. 技术可行性分析

### 3.1 候选技术方案对比

针对后端服务、Web 管理端、Android 借款端，分别提出多种可选方案并进行对比。

#### 3.1.1 后端技术方案对比

| 方案 | 技术栈 | 优点 | 缺点 | 适用性 |
| :--- | :--- | :--- | :--- | :--- |
| 方案一 | C++17/20 + Drogon | 性能高，与课程 C++ 基础衔接，能深入理解网络与并发 | 生态不如 Java/Python，开发效率较低，需要学习 Drogon | **推荐** |
| 方案二 | Java + Spring Boot | 企业级主流框架，生态完善 | 配置复杂，学习成本高，开发周期长 | 暂不采用 |
| 方案三 | Python + Flask | 开发效率高，文档丰富 | 性能较低，与课程 C++ 基础脱钩 | 暂不采用 |
| 方案四 | Node.js + Express | 前后端统一 JavaScript 语言 | 对异步编程要求较高，稳定性依赖经验 | 备选 |

**选择结论**：采用方案一 **C++17/20 + Drogon**。原因：
1. 团队成员具备一定的 C++ 学习基础，C++17/20 能够帮助深入理解底层网络与并发机制。
2. Drogon 是成熟的 C++ Web 框架，支持 HTTP、RESTful API、ORM、数据库连接池等，满足本项目需求。
3. 课程重点在于掌握软件工程流程，C++ 后端能锻炼系统设计和性能意识。
4. 同时需要控制系统规模，避免过度工程化。

#### 3.1.2 数据库方案对比

| 方案 | 技术 | 优点 | 缺点 | 选择 |
| :--- | :--- | :--- | :--- | :--- |
| 方案一 | MySQL | 关系型数据库，支持复杂查询，与 Drogon 配合有成熟驱动 | 需要单独安装部署 | **推荐** |
| 方案二 | SQLite | 零配置，单文件存储 | 不适合多人并发协作，Drogon 对 MySQL 支持更好 | 开发原型可用 |
| 方案三 | PostgreSQL | 功能强大，扩展性好 | 配置稍复杂 | 备选 |

**选择结论**：采用 **MySQL**。原因：MySQL 是课程教学中常见数据库，关系型结构适合个贷业务，且 Drogon 对 MySQL 有良好支持。

#### 3.1.3 Web 前端技术方案对比

Web 前端分为 **Web 用户端** 和 **Web 管理端**，可分别选择组件库。

| 方案 | 技术栈 | 优点 | 缺点 | 选择 |
| :--- | :--- | :--- | :--- | :--- |
| 方案一 | Vue 3 + Element Plus（管理端）+ Vant（用户端） | 组件库成熟，管理端与用户端都有优秀生态 | 需要学习 Vue 语法 | **推荐** |
| 方案二 | 原生 HTML/CSS/JS | 无框架依赖，学习成本低 | 代码组织较差，维护困难 | 备选 |
| 方案三 | React + Ant Design | 生态强大 | 学习成本较高 | 暂不采用 |

**选择结论**：采用 **Vue 3 + Element Plus（管理端）+ Vant（用户端）**。原因：
- Vue 3 语法统一，便于一人同时维护两个 Web 端。
- Element Plus 适合管理后台的表格、表单、统计展示。
- Vant 适合移动端 H5 用户端的页面布局和交互。
- 代码组织方式一致，降低学习成本。

#### 3.1.4 Android 借款端技术方案对比

| 方案 | 技术 | 优点 | 缺点 | 选择 |
| :--- | :--- | :--- | :--- | :--- |
| 方案一 | Android Studio + Kotlin | 现代 Android 官方推荐语言，代码简洁 | 团队可能需要额外学习 | **推荐** |
| 方案二 | Android Studio + Java | 与课程教学内容完全对应，资料丰富 | 代码相对冗长 | 备选 |
| 方案三 | Flutter 跨平台 | 一套代码多端运行 | 超出课程要求，学习成本大 | 暂不采用 |

**选择结论**：采用 **Android Studio + Kotlin**。原因：Kotlin 是现代 Android 开发的主流语言，代码更简洁，且与 C++ 后端形成互补。

### 3.2 技术风险与对策

| 风险点 | 影响 | 应对措施 |
| :--- | :--- | :--- |
| 团队成员对 Drogon/C++ Web 不熟悉 | 开发进度延迟 | 提前学习 Drogon 官方示例，从简单 Hello World 开始 |
| Android 网络请求调试困难 | App 与后端联调受阻 | 使用 Postman 先测试接口，再接入 App |
| 数据库设计不合理 | 后续扩展困难 | 先完成核心 E-R 图设计，再编码 |
| 多端数据格式不一致 | 联调 Bug 多 | 统一定义 JSON 数据格式和接口契约 |
| C++ 内存管理问题 | 出现崩溃或泄漏 | 使用现代 C++（智能指针、RAII），避免裸指针 |

### 3.3 技术可行性结论

本项目所采用的技术栈均为成熟、开源、社区活跃的技术，C++17/20 + Drogon 能够满足中小型 Web 后端需求。虽然 C++ Web 开发效率低于 Java/Python，但通过合理控制系统规模和充分学习，技术上完全可行。

## 5. 操作可行性分析

- **借款用户**：通过 Android App 完成注册、申请、查询，界面简洁，操作流程符合常见金融 App 习惯。

- 后端部署在本地 Linux 环境或轻量服务器上，Drogon 内置 HTTP 服务器可满足课程演示需求。

### 5.3 操作可行性结论

系统操作流程直观，运维方式简单，操作层面可行。

## 6. 法律与合规可行性分析

### 6.1 法律法规要求

参考《个人贷款管理办法》（2024）等相关法规，互联网个人贷款业务需满足：
- 借款人身份真实有效；
- 贷款用途合法合规；
- 利率披露透明；
- 个人信息保护符合相关法律法规。

### 6.2 本阶段处理方式

- 本系统为课程演示项目，使用模拟数据，不涉及真实金融业务。
- 用户注册需填写真实姓名、身份证号等模拟信息，系统设计时预留隐私保护字段。
- 利率、费用等信息在界面上明确展示。
- 不存储真实敏感信息，避免合规风险。

### 6.3 法律可行性结论

作为教学演示系统，在明确标识为模拟系统、不使用真实用户数据的前提下，法律风险可控。

## 8. 结论

综合技术、经济、操作、法律四个维度的分析，本项目在当前团队能力、课程要求和资源条件下**完全可行**。建议采用以下技术方案：

- 后端：C++17/20 + Drogon + MySQL
- Web 管理端：Vue 3 + Element Plus
- Android 借款端：Android Studio + Kotlin
- 接口协议：RESTful API + JSON
- 服务器环境：Linux / Ubuntu

项目组应按照可行性分析结论，进入需求分析和系统设计阶段。
