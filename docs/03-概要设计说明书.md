## 1. 引言

### 1.1 编写目的

本文档对“多数据源融合的互联网个人贷款风控系统”基本版进行概要设计，明确系统架构、模块划分、技术选型、数据库设计和接口规划，为详细设计和编码实现提供总体框架。

### 1.2 设计目标

- 采用分层架构，保证系统结构清晰、职责单一。
- 借款端与管理端通过统一的后端 API 交互，降低耦合。
- 预留风控接口，便于后续阶段实现多数据源融合风控。
- 设计合理的数据库结构，支持核心业务流程。

## 2. 系统架构设计

### 2.1 总体架构

系统采用经典的 **B/S + C/S 混合架构**：

```text
┌─────────────────┐      ┌─────────────────┐
│  Android 借款端  │      │  Web 审批管理端  │
│  (Kotlin)        │      │   (Vue 3)        │
└────────┬────────┘      └────────┬────────┘
         │                        │
         │      HTTP / JSON       │
         └──────────┬─────────────┘
                    │
         ┌──────────▼──────────┐
         │   C++ 后端服务      │
         │  (Drogon)           │
         │  - Controller       │
         │  - Service          │
         │  - DAO              │
         │  - 风控接口预留     │
         └──────────┬──────────┘
                    │
         ┌──────────▼──────────┐
         │      MySQL 数据库    │
         └─────────────────────┘
```

### 2.2 C++ 后端分层架构

后端服务内部采用分层架构：

| 层次 | 职责 | 对应模块 |
| :--- | :--- | :--- |
| Controller 层 | 接收 HTTP 请求，解析 JSON，调用 Service，返回 JSON | `controller/` 目录下各类 |
| Service 层 | 处理业务规则、状态流转、风控调用 | `service/` 目录下各类 |
| Model 层 | 定义数据实体 | `model/` 目录下各类 |
| DAO 层 | 数据库连接与 SQL 操作 | `dao/` 目录下各类 |
| Common 层 | 统一返回结果、异常处理、工具函数 | `common/` 目录下各类 |

## 6. 接口设计

### 6.1 接口设计原则

- 采用 RESTful 风格，使用 HTTP 方法区分操作类型。
- 请求与响应数据格式统一为 JSON。
- 接口路径以 `/api` 开头。
- 除登录、注册外，其他接口需携带 JWT Token。

### 6.2 接口列表

| 接口组 | 接口路径 | 方法 | 说明 |
| :--- | :--- | :--- | :--- |
| 用户 | `/api/register` | POST | 用户注册 |
| 用户 | `/api/login` | POST | 用户登录 |
| 用户 | `/api/users/{id}` | GET | 获取用户信息 |
| 用户 | `/api/users/{id}` | PUT | 更新用户信息 |
| 产品 | `/api/loans` | GET | 获取贷款产品列表 |
| 贷款 | `/api/loans/apply` | POST | 提交贷款申请 |
| 贷款 | `/api/loans/{id}` | GET | 查询贷款详情 |
| 贷款 | `/api/users/{id}/loans` | GET | 查询用户贷款列表 |
| 审批 | `/api/approval/list` | GET | 获取待审批列表 |
| 审批 | `/api/approval/{id}` | GET | 查询审批详情 |
| 审批 | `/api/approval/{id}/approve` | POST | 通过审批 |
| 审批 | `/api/approval/{id}/reject` | POST | 拒绝审批 |
| 还款 | `/api/repayments` | GET | 查询还款计划 |
| 还款 | `/api/loans/{id}/repayments` | GET | 查询某笔贷款的还款计划 |
| 风控 | `/api/risk/evaluate` | POST | 风控评分（模拟） |
| 统计 | `/api/statistics/overview` | GET | 获取统计概览 |
| 管理 | `/api/admin/login` | POST | 管理员登录 |

### 6.3 接口认证方式

- 用户登录成功后返回 `access_token`。
- 后续请求在 HTTP Header 中携带：`Authorization: Bearer <token>`。
- 后端解析 Token 验证用户身份。

## 7. 安全策略

### 7.1 身份认证

- 借款用户和管理员分别使用不同的登录接口和 Token。
- 使用 JWT 实现无状态认证。

### 7.2 数据安全

- 用户密码使用 bcrypt 等算法加密存储。
- 数据库连接信息不硬编码，使用配置文件或环境变量。
- 使用参数化查询防止 SQL 注入。

### 7.3 传输安全

- 课程演示阶段可使用 HTTP。
- 生产环境建议启用 HTTPS。

## 8. 部署架构

### 8.1 开发环境

- 后端、Web 管理端、MySQL 均运行在 Linux 本机或 WSL2。
- Android App 通过本机 IP 或模拟器访问后端。

- 数据库部署在同一台服务器。

## 9. 关键设计决策

| 决策点 | 方案 | 理由 |
| :--- | :--- | :--- |
| 后端框架 | C++17/20 + Drogon | 利用 C++ 基础，性能高，满足 HTTP/REST API 需求 |
| 数据库 | MySQL | 关系型数据库，适合个贷业务，Drogon 支持好 |
| Web 前端 | Vue 3 + Element Plus | 组件丰富，适合管理后台 |
| Android | Kotlin + Android Studio | 现代 Android 开发语言，代码简洁 |
| 接口协议 | RESTful + JSON | 通用、与 Android 网络章节衔接 |
| 认证方式 | JWT | 无状态、实现简单 |
| 风控 | 仅预留接口 | 符合本阶段任务书要求 |

## 10. 风险与应对

| 风险 | 影响 | 应对措施 |
| :--- | :--- | :--- |
| C++/Drogon 学习曲线 | 开发进度延迟 | 提前学习官方示例，从简单接口开始 |
| 多端接口不一致 | 联调困难 | 先定义接口契约，使用 Postman 测试 |
| 数据库设计变更 | 影响多个模块 | 先完成概要设计再编码 |
| Android 页面适配 | UI 效果差 | 使用 ConstraintLayout，避免写死尺寸 |
| C++ 内存问题 | 崩溃或泄漏 | 使用智能指针、RAII、代码审查 |
| 时间不足 | 功能无法完成 | 优先完成 MVP，再扩展功能 |
